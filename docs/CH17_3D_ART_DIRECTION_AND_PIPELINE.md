# 第十七號門｜3D 美術目標與場景製作路線（2026-11-15）

> **狀態：已討論的美術目標＋待驗證的技術建議。** 這是供 Claude 與其他開發者對齊方向的規範，不代表下述改造已完成或已獲准一次全面實施。不得因此擅自改動 Unity 專案、正式場景、提燈機制或玩家操作。

## 1. 美術目標（已確認）

- 目標：**Stylized Semi-Realistic 3D with Painterly Materials**（帶繪畫質感的風格化半寫實 3D）。
- 期望玩家感到「**一個帶有繪畫質感的真實世界**」，**不是**「一部可以玩的動畫電影」，也不是平面插畫、強烈賽璐璐卡通、照片寫實或套全螢幕油畫濾鏡。
- 重要要求：**保留清楚的三維體積、空間深度、材質厚度與接觸陰影**。過去的 AI 概念渲染被認為太平面，不能把「繪畫感」誤解為壓平形體、消除光照漸層。
- 建築與家具保留可信的大形體、清楚輪廓、概括化細節；材質呈現受控的紋理與輕微筆觸；光影有柔和過渡、明暗層次與焦點；整體成熟、暗黑都市奇幻，不走過度動畫化。
- **褪色態是玩家進入異域的預設狀態**，本身也要有足夠辨識度、立體感與探索可讀性；提燈照出的記憶態偏向另一種局部顯現的時空/記憶，不是「漂亮版全屋切換」。兩態的玩法規範詳見 `docs/CH17_LANTERN_DUAL_STATE_EXPLORATION.md`。

## 2. 對現況的技術盤點（Claude 提供的唯讀稽核；尚未由本文件重新執行 Unity 驗證）

- Unity 2022.3.18f1；URP 14.0.10，Forward+。
- `LanternPrototypeQA.Setup() → LanternGraybox.Build() → BuildHouseV2()`：目前房屋大多在執行時由 C# 建構；建築使用 `Box/Cyl/Ball` 等基本幾何；主要檔案為 `LanternGraybox.cs`、`LanternHouse.cs`、`LanternHouseV2.cs`、`LanternDining.cs`。
- Blender 匯入的 `dn_*`、`v2_*` 家具雖是獨立模型，但不少由基本形狀與倒角組成；目前仍有大量單色材質、缺乏法線與表面變化。
- 主要自訂 Shader：`LanternReveal.shader`，承擔褪色／提燈局部揭露及 URP PBR 光照；`LanternPaint.shader` 全螢幕繪畫濾鏡目前關閉，不應未經視覺驗收直接開啟。
- 有部分 Poly Haven 2K 貼圖與 SSAO、ACES、Bloom、調色等後製；目前以即時光為主，環境光偏單一，缺少已配置的反射/光照探針與烘焙 GI。
- **重要區分**：以上是目前稽核結果，不代表程式化建構必然造成低畫質，也不代表執行時生成完全不能使用反射探針或間接光。不可把「換 Shader」當成唯一解方。

## 3. 問題與優先順序

1. **材質**：單色表面過多，木材、布料、牆面與陶瓷缺少可信的粗糙度、法線、色彩變化。
2. **光照與反射**：間接光與環境層次不足，物件容易像獨立被照亮的模型，缺乏自然的空間關係。
3. **模型幾何**：門窗、線板、重要家具的輪廓與截面過於方塊化，Shader 無法憑空創造造型。
4. **風格一致性**：現有 Shader 以 PBR 為主，尚未形成完整的 Painterly 材質語言；後製不能取代模型、貼圖和燈光。
5. **製作流程**：完全在 Play 時生成使美術手動微調、儲存場景及傳統烘焙工作流程不便。

這是**目前的工作假設與優先方向**，實際視覺改善幅度必須透過同機位 QA 對照確認。

## 4. 建議的低風險實驗順序（尚未授權全面改造）

1. **先固定餐廳為獨立美術 QA 測試範圍**，保留正式場景與現有探索/門/提燈行為；同一相機角度拍攝原版與實驗版，褪色態及提燈照射區都要比較。
2. **先改善材質與光照**：測試現有貼圖合理套用、粗糙度/法線、環境光層次、反射探針或其他可行反射方案。不可聲稱反射探針就等於真正鏡面反射；鏡子的實現需另行驗證。
3. **精修少數關鍵模型**：例如門框斷面、餐桌或壁爐，檢驗提升模型輪廓是否比堆疊細節更有效；其他家具暫不重做。
4. **最後比較風格化材質/Shader**：保留 `LanternReveal` 的局部光照雙態機制、可見性及碰撞設計；不可先套全畫面繪畫濾鏡造成平面感。
5. **評估可編輯場景工作流程**：研究「C# 生成基礎房屋 → 在 Unity 編輯器保存可調整的場景或 Prefab → Blender 精修與 Unity 美術擺設 → 遊戲執行時保留異域動態效果」的可行性。先做餐廳小型試驗，**不要直接刪掉生成程式或一次轉換全屋**。
6. 經使用者檢視並認可實際截圖後，才討論是否擴展至其他房間。

## 5. 驗收與協作限制

- 不得為了渲染測試更改已確認的房屋格局、玩家動線、相機、門、家具位置、提燈玩法、互動或全域 UI。
- **實機渲染與 AI 圖像風格模擬必須清楚區分**；概念圖不能當成 Unity Shader 已實現的證據。
- QA 需提供固定機位的前後比較、褪色態、提燈照亮區域、近看材質及通行/互動回歸結果。未執行的測試要明說。
- Unity/Blender 由 Claude 與現有開發工作流分工；不同 session 不得同時修改同一功能或覆蓋彼此未提交的內容。
- 這份文件是**設計對齊與技術路線**，不是立即開工命令。後續每次實作都須先核對現有程式和實際 QA，明確界定本次要改的項目。
